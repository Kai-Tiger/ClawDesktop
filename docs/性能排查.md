# 性能排查记录（OpenClaw Desktop）

本文汇总本次排查中关于 **长耗时、超时、token 过高、上下文注入来源、skill 目录一致性** 的结论与改动，便于后续复盘。

## 一、现象与核心问题

### 1) HTTP 卡住或失败
- 典型日志：`TypeError: fetch failed`、长时间无响应。
- 早期请求出现约 5 分钟后失败（接近默认上限）。

### 2) 回退 CLI 后仍长时间无结果
- HTTP 超时后会进入 CLI fallback。
- 部分任务中 CLI 也超时，最终 UI 显示 `(无回复内容)`（已修复为明确超时文案）。

### 3) 文件行数与执行结果不一致
- 用户上传 40 行文件，但 agent 产生了 93/130+ 的执行报告。
- 排查确认是“前一条仍在跑时，队列消息被并入最终 prompt（Queued user message）”。

### 4) prompt token 过高
- 同样文本长度（`textLen`）下，`prompt_tokens` 差异巨大。
- 主要原因不是用户正文，而是 runtime 注入上下文（AGENTS/TOOLS/skills/工具 schema/会话态）。

## 三、已实施改动

### 1) HTTP/CLI 超时机制完善
- 初始：统一超时后，逐步改为分离。
- 当前：
  - HTTP 超时：`300s`
  - CLI 超时：`600s`
- 文件：`app/electron/main/index.ts`

### 2) 超时文案回传 UI
- HTTP 超时后若切入 CLI，会在最终回复前加提示：
  - `⚠️ HTTP...请求超时，已切换到 CLI 继续处理。`
- CLI 超时时，返回明确错误：
  - `调用失败: CLI 执行超时（>...ms）`
- 修复了“CLI 超时但 code=1 导致显示 `(无回复内容)`”的问题。

### 3) `/Clear` 同时清 backend session
- 之前 `/Clear` 只清 UI 消息。
- 现在会同时调用 `clearWorkerSessions(...)`，清理会话快照，减少历史残留串单。
- 文件：`app/electron/renderer/src/components/Chat/Composer.tsx`

### 4) HTTP usage 记录增强
- 将主进程日志从 `usageKeys` 改为完整 `usage={...}`。
- 文件：`app/electron/main/index.ts`

### 5) trace 脚本支持提取 token usage
- `trace-message-chain.py` 增加 usage/token 解析逻辑，尽量从日志与custom数据提取完整 token 字段。

### 6) 请求前上下文 dump（调试）
- 新增文件：
  - `runtime/logs/tool-schema-dump.json`
  - `runtime/logs/tool-schema-dump.jsonl`
  - `runtime/logs/tool-schema-dump-<traceId>.json`
- 内容包括：`SOUL/AGENTS/TOOLS` 字符数、skills 列表及 `SKILL.md` 大小、memory 目录摘要、引用路径等。

### 7) prompt 注入来源切换为 workspace
- HTTP 组装上下文读取路径从 `workers/<id>` 改为 `workspace-<id>`。
- 避免“删了 workspace skill 但仍被 workers skill 注入”的错觉。

### 8) skill 导入双写
- 页面导入 skill 时，同时写入：
  - `workspace-<id>/skills`
  - `workers/<id>/skills`
- 目的是降低源目录与运行时目录漂移。

## 四、目录职责（最终口径）

### `workers/<workerId>`
- 源定义目录（模板/配置源）。

### `workspace-<workerId>`
- 运行时目录（执行产物、memory、临时文件、对话生成文件等）。

### 当前策略
- 注入读取：优先 workspace（已改）。
- skill 导入：workers + workspace 双写（已改）。

## 五、关于 token 分布的解释口径

### 能精确给出的
- provider 返回的 `prompt_tokens/completion_tokens/total_tokens`。

### 不能精确给出的
- provider 没有逐项 token 账单（例如“AGENTS 占多少 token、skills 占多少 token”的官方值）。

### 可近似分析的
- 通过 `tool-schema-dump-<traceId>.json` 的字符分布评估相对占比：
  - 用户正文通常占比较小；
  - `AGENTS/TOOLS/skills` 往往是主要贡献；
  - runtime 仍有内部组装部分，可能形成额外 token。

## 六、后续建议

1. 增加“仅注入命中 skill（Top-K）”策略，减少全量 skills 带来的 token 膨胀。
2. 新增“忙碌态拒绝/覆盖队列”策略，避免 queued message 串单。
3. 在 UI 发送前展示摘要：目标 worker、内联文件名、行数、预估上下文体积。
4. 将 `idleTimeoutSeconds` 明确写入配置并与 HTTP/CLI 超时协同管理。
