- preload 把请求转发到主进程 ipcMain.handle('chat:send')（preload/index.ts:22, main/index.ts:1713）。

- chat() 先判断是否有图片；如果是 agent worker 且有图片，强制走 HTTP 视觉路径，不走 CLI（main/index.ts:999）。

  这里面哪些是openclaw层面处理的
  主要从 POST /v1/chat/completions 开始，就是 OpenClaw 层面的处理了。你这条链路可以这样切分：
- 应用层（Electron/前端）负责
  - 选图、校验、转 base64（Composer.tsx）
  - 组装 images: [{ mediaType, data }] 并通过 IPC 发给 main（useChat.ts / preload）
  - 在 main 里把 worker 的 SOUL.md、AGENTS.md 拼进 messages
  - 把图片转成 data:<mime>;base64,... 的 image_url 结构
- OpenClaw 层面负责（核心）
  - 接收你发到 http://127.0.0.1:<port>/v1/chat/completions 的请求
  - 解析 messages（包括 image_url 的 data URL）
  - 根据当前 gateway/model 配置路由到底层模型提供方
  - 执行真正的多模态推理（图像理解 + 文本生成）
  - 返回统一格式响应（choices/output_text/...）
- 回到应用层负责
  - 你这边 extractReplyText() 只是从 OpenClaw 返回里“取文本”
  - 再把结果显示到 UI
    一句话：图片“预处理和打包”在你 app，图片“理解和推理”在 OpenClaw（及其下游模型）。

我现在的问题是，要做一个可以识别图片内容并给出优化建议的skill，要怎么实现，需要增加一个工具脚本吗
可以做，而且你这个需求里不一定要先加工具脚本。  
先说结论：

- 仅做“看图 + 给优化建议” → 先不用脚本，靠多模态模型 + skill 规则就够。
- 要做“可量化检测”（尺寸、清晰度、OCR 文本、对比度、留白比例等）→ 再加工具脚本更稳。
  但你现在有一个关键点要先处理：
- 在你当前代码里，agent + 图片 走的是 HTTP 视觉路径（main/index.ts:999），而不是 CLI agent 路径。
- 这通常意味着：图片请求时，skill 机制可能不会按你预期参与（至少不是完整的 agent+tools 流程）。
  所以实现上建议这样：

1. 先确认链路

- 你要的“图片优化 skill”如果依赖 skill/tool，最好让图片请求进入 agent 流程。
- 否则就把“优化规则”写到 SOUL.md/AGENTS.md，让 HTTP 视觉路径直接按规则输出。

2. 先做无脚本版（推荐起步）

- 在 skill（或 system prompt）里固定输出框架：
  - 画面理解（主体/场景/文案）
  - 关键问题（最多 5 条）
  - 优化建议（按优先级 P0/P1/P2）
  - 可直接执行的修改指令（给设计/运营/文案）
- 这版最快上线，效果通常已经不错。

3. 再决定是否加脚本

- 需要“客观指标”时再加工具，比如：
  - 读取分辨率、长宽比、文件大小
  - OCR 提取文字并检查错别字/密度
  - 基础对比度/清晰度估计
- 让模型“主观建议 + 工具客观数据”一起输出，稳定性会更高。
